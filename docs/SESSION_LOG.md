## 一、AI 帮上大忙的地方

不掩饰：这个项目的骨架基本是 AI 写的。有几处如果让我从零写，会花掉几倍时间：

1. **FFmpeg 参数体系**。`-cq` 和 `-crf` 的语义差别、NVENC 必须带 `-b:v 0` 否则落到固定码率模式、
   10bit 源默认输出 `yuv420p10le` 导致微信放不出来——这些知识散落在文档各处，AI 一次就给了全，省了大量试错。

2. **正则表达式**。`ffmpeg -i` 的 stderr 格式极其不规则，AI 给的正则基本可用。

3. **QSS 样式表**。Qt 的 QSS 是门半吊子语言，我写了 200 行浅色主题，一次成型。

4. **单元测试的边界用例**。我提示"这个函数哪里容易错"，AI 能列出 `out_time_us=N/A`、
   零时长除零、百分比越界这些我自己未必想全的边界。

## 二、AI 做错、我抓出来的 7 件事

这一节是这份文档的重点。每条都是**AI 给出的东西看起来对，但跑起来错**。

### 1. 编码器探测的假阴性：`-f null` 不支持硬件编码

**AI 给的探测命令**：

```bash
ffmpeg -f lavfi -i testsrc=size=320x240:rate=10:duration=1 -an -c:v h264_nvenc -f null -
```

**现象**：报 `-22 Invalid argument`。

**我做的排查**：先怀疑像素格式（`testsrc` 输出 RGB，硬件编码器只吃 yuv420p），
加了 `-pix_fmt yuv420p` ——还是失败。换成原生 yuv420p 的 `testsrc2` ——还是失败。
最后把 `-f null -` 换成真实文件输出，**依然失败**，但这次我加了 `-v verbose`：

```
[h264_nvenc] Loaded Nvenc version 13.0
[h264_nvenc] Driver does not support the required nvenc API version. Required: 13.1 Found: 13.0
[h264_nvenc] The minimum required Nvidia driver for nvenc is 610.00 or newer
```

**真因**：这台机器是 RTX 5060 + 驱动 573.24，而这个 ffmpeg 构建要求驱动 ≥ 610.00。
跟像素格式、跟 `-f null` 都没关系。

**反馈到产品上**：如果探测只输出"失败"，用户只知道"没有硬件加速"，不知道为什么。
所以 `infra/ffmpeg_bin.py` 里加了一层 `diagnose()`，把 stderr 里的关键词翻译成人话，
界面上直接显示「使用 CPU 编码（NVIDIA NVENC：显卡驱动版本过低，需要更新到 610.00 或更高）」。
**这个降级解释能力，比"能硬件加速"更能体现产品成熟度。**

### 2. AMF 的假阳性：探测"通过"了，但根本不能用

**现象**：探测脚本报告 `✓ h264_amf 259ms 可用`，界面显示"使用 AMD AMF 硬件加速"。
可这台机器是 NVIDIA 显卡，而且 `params.py` 里**根本没实现 AMF 的参数分支**，
实际执行的还是 `libx264`。

**危害**：这比不显示更糟——用户以为自己在用硬件加速，实际上没有。

**修法**：把候选编码器从 4 个砍到 2 个（`h264_nvenc` → `libx264`）。
理由写进代码注释：QSV 在笔记本双显卡上失败率极高，AMF 在无 AMD 卡时存在假阳性，
而且**程序只实现了这两种编码器的参数，多探一个就多一个说谎的机会**。

> 教训：探测能力必须和实现能力对齐。能探测但不会用，就是在制造误导。

### 3. 目标体积大于源文件 → 文件被"注水" 659%

**现象**：冒烟测试输出 `✓ 转码成功 253KB → 1.9MB，↑659.9%`。压小一点，结果大了 6 倍。

**原因**：需求是"压到 20MB"，但源文件只有 253KB。码率反推公式算出的目标码率是 16288k，
远高于源码率——"压缩"变成了"提高码率"。

**修法**：`params.py` 里加判断——

```python
if not info.size_bytes or target_bytes < info.size_bytes:
    bitrate = estimate_bitrate_kbps(...)
```

目标体积不小于源文件时，说明体积不构成约束，退回质量模式，至少画质不会倒退。
同时补了一个单测钉住这个行为。

### 4. 只给 `-b:v` 管不住体积：目标 20MB 实际出 38MB

**现象**：43MB 素材，目标 20MB，转完是 38.2MB，只降了 10.1%。

> 这里的 43MB 指的是当时那版 5 秒噪声素材（见第七节，后来被换掉了）。
> 换成 11 秒三幕短片之后，同一组参数实测是 59MB → 17.2MB。

**原因**：x264 在给了 `-b:v` 后走 ABR 模式，而 ABR 需要若干秒才收敛到目标码率。
5 秒的短视频还没收敛就结束了。这不是 bug，是编码器的固有行为。

**修法**：加 `-maxrate`（1.2 倍目标码率）和 `-bufsize`（2 倍）硬约束峰值。

```python
args += ["-b:v", f"{bitrate_kbps}k",
         "-maxrate", f"{int(bitrate_kbps * 1.2)}k",
         "-bufsize", f"{int(bitrate_kbps * 2)}k"]
```

**效果**：同一素材，43MB → 18MB，误差 10% 以内。

> 教训：AI 知道 `-b:v` 的用法，但不会主动告诉你它在短视频上不靠谱。
> 这类"参数能用但不准"的知识，只能靠实测发现。

### 5. `str.format()` 把 JSON 示例当成占位符，直接 KeyError

**AI 写的代码**：

```python
PLAN_SYSTEM_PROMPT = '''...{"preset": "...", "video": {"codec": "{codec_options}"}}...'''
system = PLAN_SYSTEM_PROMPT.format(codec_options=..., scale_options=...)
```

**现象**：`KeyError: '\n  "preset"'`。提示词里 JSON 的 `{` 被当成了占位符起始。

**危害**：这个异常发生在"载入文件后自动生成默认方案"的路径上，
导致整个载入流程中断——用户看到的是信息和缩略图都出来了，但右侧全部是空的、
按钮点了没反应。**界面没有报错，只是"不能用"**。

**修法**：两处。
1. 提示词改用 `__CODEC_OPTIONS__` 这种不会和 JSON 冲突的占位符，用 `str.replace` 注入
2. `_on_video_loaded` 里给顾问加 try/except 兜底——顾问挂了不能连累"文件已载入"这件已完成的事

> 教训：**信号槽里抛出的异常不会弹窗**，只会写进 stderr。
> 所以必须有全局异常钩子（`app.py` 里已加）+ 关键路径的 try/except，
> 否则用户只会看到"点了没反应"。

### 6. QSS 只写 `padding-right` 会吃掉上下内边距，文字被裁半个字

**现象**：截图里分辨率显示成 `/20p`、目标体积只露出 `20.0 MB` 的上半截。

**原因**：我给数值框加了 `padding-right: 22px`（为了给自绘箭头留位置），
这个写法覆盖了整个 `padding` 简写，上下内边距归零，控件高度被压缩。

**修法**：写全四个方向 `padding: 7px 22px 7px 10px`，并给所有输入控件补 `min-height: 20px`。

> 这个 bug 只有**看图**才能发现——单元测试全绿，程序逻辑完全正常，
> 只是界面难看到不能用。所以我在 `scripts/e2e_ui.py` 里做了自动截图，
> 每次改完界面都出图自查。

### 7. 打包后样式表静默丢失（开发态完全正常）

**现象**：`VideoBox.exe` 能启动、功能正常，但界面是 Qt 默认的灰扑扑样式。
日志里只有一行 WARNING：

```
[WARNING] 样式表未找到：...\_internal\ui\style.qss（将使用 Qt 默认外观）
```

**原因**：资源路径在两种状态下层级不同——

- 开发态：`videobox/ui/style.qss`
- 打包后：`_internal/videobox/ui/style.qss`

我原来的 `_resource_path()` 少拼了一层 `videobox`。

**修法**：frozen 时补上 `videobox/` 前缀。

> 教训：**打包是独立的一次验收**，不能假设"开发态跑通 = 打包后没问题"。
> 这也是为什么我把打包提前到第二天晚上做，而不是留到最后——
> 第一次打包必然踩坑，留到最后就是赌博。

## 三、几个我主动做的、AI 不会替你想的决定

| 决定 | 理由 |
|---|---|
| 砍掉九宫格缩略图 | 要真解码 8 秒素材，慢；而要求只说"缩略图"，单帧已达标。时间要花在更能体现工程能力的地方 |
| 砍掉 QSV / AMF 探测 | 探了也用不了（见第 2 条），探测能力要和实现能力对齐 |
| 砍掉 Inno Setup 安装包 | 双击 exe 就能用，安装包是纯加分项，优先级低于单测和文档 |
| AI 输出禁止包含命令串 | 只允许从枚举选值，命令由程序拼装。否则一句精心构造的提示词就能让程序执行任意 ffmpeg 参数 |
| 无 Key 时走完整本地规则引擎，而不是写死一句"请配置 Key" | 审核人第一次打开时大概率没有 Key。如果那时功能是残的，AI 能力就等于不存在 |
| 结果行必须显示实际体积，而不是只显示"已完成" | 自查时发现 20MB 目标出了 38MB，就是因为没把实际数字摆出来 |

## 四、如果还有时间，我会做什么

按优先级：

1. **两遍编码精确控体积**。现在单遍 + `maxrate` 能把误差控制在 10% 左右，
   两遍编码可以做到 2% 以内，代价是耗时翻倍。
2. **批量队列**。这次的界面刻意没做队列（左栏留给了大缩略图），单文件转码是主场景。
   真实用户一次转十几个文件时，队列是刚需。
3. **九宫格时间轴预览**。抽 9 帧拼图，成本是一次解码，但对"找片头"场景很有用。
4. **macOS / Linux 适配**。`params.py` 和 `core/` 完全跨平台，
   主要是 `ffmpeg_bin.py` 的路径探测和 QSS 需要调整。

## 五、交付阶段又踩了三个坑

写代码的坑在前四节，这一节是"做完之后发不出去"的坑——比写代码更消耗时间。

### 1. Release 显示成功，附件却是空的

`gh release create` 返回了 URL，我当时以为完事了。回头核实：

```
Draft  v1.0.0  2026-10-29T07:33:15Z     ← 是草稿
assets: []                              ← 附件没上去
```

**教训**：CI/CD 里"命令返回 0"和"结果正确"是两件事。凡是有外部副作用的操作，
都要回头用一个**独立的读操作**验证（这里是 `gh release view --json`）。
现在把附件重新上传、确认 size=161418115、再把 draft 改成正式版，才算是真的发出去。

### 2. `git push` 反复 502，最后绕道 REST API

推送时不断报 `CONNECT tunnel failed, response 502` / `Empty reply from server`。
排查顺序：
1. 以为是代理配置问题 → 关掉代理直连 → `Could not connect`（这台机器直连 GitHub 本来就不通）
2. 改 `http.version=HTTP/1.1`、调大 `postBuffer` → 无效
3. 发现 `gh api rate_limit` 一直是通的 → **同一个网络下，git 的 smart HTTP 通道挂了，API 通道活着**

于是改用 REST API 手工完成推送：`POST /git/blobs`（每个文件 base64）→
`POST /git/trees`（带 base_tree，只放改动的文件）→ `POST /git/commits` →
`PATCH /git/refs/heads/master`。四步等价于一次 `git push`，副作用是远端多了一个
内容相同但 SHA 不同的提交，本地 `reset --hard` 对齐即可。

**这不是常规操作**，只在网络受限时用。但它说明一件事：知道工具在协议层做了什么，
才有条件在工具失效时用别的方式达到同样目的。

### 3. 演示 GIF：录屏是错的方向

第一反应是 OBS/ffmpeg gdigrab 录桌面，立刻发现三个问题：会录进任务栏和通知弹窗、
DPI 缩放导致裁剪偏移、换台机器就不可复现。

改成**应用进程内按帧 `grab()` 窗口**，再交给 ffmpeg 两遍法（`palettegen` + `paletteuse`）合成。
好处是像素干净、尺寸固定、每次跑都是同一套真流程。

中间还错了一次：想用 `fps=3` 把 4.7 秒的流程放慢，结果时长还是 4.66 秒——
`fps` 滤镜只丢帧、**不拉伸时间轴**。正确做法是把**输入帧率**设成 3，让每帧停留 1/3 秒。
这是唯一一处刻意偏离真实速度的地方，README 里写明了。

## 六、第八个 bug：加完打磨功能，顺手撞出来的

这一条发生在"补客户端细节"之后，值得单独写，因为它是**在验证另一个功能时偶发**、
而不是在写那部分代码时出现的——这类 bug 才是真实项目里最耗人的。

**场景**：为了验证 `QSettings` 有没有真的把窗口位置写进去，我写了个脚本：
启动主窗口 → 立刻 `close()` → 读注册表。

**现象**：窗口关闭后，启动阶段提交的环境探测任务还没跑完（要实测两个编码器，约 1 秒），
结果回来时接收者已经销毁，Qt 打出：

```
Error calling Python override of QRunnable::run():
  RuntimeError: Signal source has been deleted
```

**为什么这是真问题而不是噪音**：用户双击程序、看一眼、发现点错了文件、一两秒内就关掉——
这是极常见的动作。此时后台线程仍在 emit，异常会冒到 Qt 层；而 `--noconsole` 打包后
这类输出**用户根本看不见**，程序只是"安静地出了点事"。

**修法**：把 emit 收进一个 `_emit()` 守卫，`RuntimeError` 时丢弃结果并记一行 debug。
重点不是 try/except 本身，而是**承认"结果来得太晚"是一种正常情况，不是错误**。

**顺带补了 4 个测试**（`tests/test_tasks.py`）：死信号不抛、活信号照常收到、
成功发结果、失败发失败并把异常吞掉。测试数从 50 变成 54。

这条 bug 也算回答了一个常见疑问：**为什么自动化测试之外还要手工点**。
它不是被"写代码"发现的，是被"验证另一个功能"顺手发现的。

## 七、第九个 bug：演示素材自己就是一团雪花

**现象**：一位朋友看完 README 顶部的 GIF 之后说了一句话——
「demo 视频乱码得很，本身的视频就不是完整的一个可以看的视频」。

**根因**：演示素材是我用 `testsrc2` 加全屏噪声生成的：

```
-f lavfi -i testsrc2=size=1920x1080:rate=30:duration=5 \
-vf noise=alls=16:allf=t+u
```

当时的想法是"测试图案没有冗余，压不动，加噪声才有真实压缩空间"。这个想法
在**码率层面**是对的，在**人眼层面**是灾难：`alls=16` 是全强度的逐帧随机噪声，
1080p 下就是一屏雪花。技术上它确实是"视频"，但没有一个人愿意看完它。

**为什么我没发现**：因为整条验证链里，没有任何一步在检查"画面是不是人想看的"。
自动化验证的是「转码成功、体积变小、进度到 100%」，我盯着体积 43MB → 18MB
这个数字很满意——**拿机器指标去验证一个给人看的东西，这就是问题本身**。
要求 7 的原话是「项目设计目标是给人用」，素材也是产品的一部分。

**修法**：换成用 ffmpeg 现场合成的三幕短片（`scripts/make_fixtures.py`）：
深色底 + 中文标题 + 卡片 + 交叉淡化 + 轻微胶片颗粒。11 秒，能从头看到尾。
顺带把体积控制在 59MB（源文件必须大于 20MB，否则 GIF 里"别超过 20MB"
这个场景会落到"目标比源文件还大"的降级分支上，演示就失效了）。

**这一步踩的两个坑**：

1. **颗粒强度与体积之间没有中间档**。噪声是纯随机信息，`alls=5` 时
   CRF 14 → 60MB、CRF 16 → 19.5MB、CRF 18 → 4MB、CRF 10 → 120MB。
   低 CRF 下编码器老老实实保留每一粒噪声，高 CRF 下直接整体量化掉，
   中间几乎没有过渡。想同时要"画面干净"和"文件够大"，得靠内容本身的细节，
   而不是靠加噪声。
2. **drawtext 里文字带的冒号必须转义**。`text='崂山日出 · 05:12'` 里的 `:` 会被
   当成滤镜参数分隔符，报出来的错还错位到了下一个滤镜上：
   `Could not set non-existent option 'drawbox' to value 'x=...'`——
   看着像 drawbox 的问题，实际是前一个 drawtext 的文字。写成 `05\:12` 才对。

**教训**：这一条和前面八条不太一样。前八条是"代码对但结果不对"，这条是
"结果对但东西不能看"。两者的共同点是——**只有真的用眼睛看过，才知道它行不行**。

## 八、一句话总结

AI 能在这个项目里承担大约 70% 的代码量，但它给出的东西**默认是"看起来对"的**。
这个项目里 9 个真 bug，没有一个是语法错误——全是"逻辑上说得通、跑起来不对"的问题：

- 探测说可用，实际不可用（2 次）
- 压缩说变小，实际变大（2 次）
- 界面说正常，实际文字被裁（1 次）
- 代码说能跑，实际抛异常且不弹窗（2 次）
- 开发说没问题，打包后失效（1 次）
- 素材说能压，实际没人愿意看（1 次）

**发现它们靠的不是读代码，而是跑起来看、截图看、看日志、在干净环境里试。**
这大概就是 JD 里写的"能够理解并检查 AI 生成的代码，独立定位和解决问题"的实际含义。
