## 1. GUI 框架：PySide6，而不是 C++/Qt 或 WPF

**背景**：岗位 JD 首个标签是 C++，框架清单里 Qt 排第一。本机其实装了
`C:/Qt/5.15.2/mingw81_64` 全套工具链和 Qt Creator，走 C++/Qt 在环境上是可行的。

**对比**：

| 方案 | 客户端关联度 | 我的现有能力 | 三天内可行性 |
|---|---|---|---|
| **PySide6** | 高（原生 Qt 控件，真 exe） | 强（Python 主力，另有 PyQt5 项目经验） | 高 |
| C++/Qt | 高 | 无 C++ 项目记录 | 低：编译、中文路径、内存管理会吃掉大半时间 |
| C# WPF | 最高 | 无 C# 经验，机器无 .NET SDK | 低 |
| Electron | 中高（易被看作网页套壳） | 强 | 中 |
| Tauri | 高 | 无 Rust，机器无 cargo | 低 |

**决策**：PySide6。

**理由**：
1. 这个岗位叫「**AI** 桌面应用开发」，GUI 是载体，AI 集成才是主战场。
   用 C++ 会把时间烧在语言上，AI 部分必然敷衍——那是拿主战场换边角料。
2. PySide6 是 Qt 官方绑定，产出原生 Qt Widgets 控件和独立 exe，
   对"界面选型必须跟客户端相关"这一条是硬达标，不擦边。
3. **选型对比本身就是要求 4 要的"开发者决策记录"**。把这份对比写清楚，
   比交一个半吊子 C++ 更能说明工程判断力。

**代价**：审核人可能会觉得"不是 C++，跟岗位标签不完全贴合"。
这个风险我认，但用"AI 集成深度 + 工程质量"来对冲。

## 2. AI 能力的落点：产品内顾问 + 开发过程记录

题目第一句是"**使用 AI 写**一个转换器"（AI 是工具），第 4 条要"会话总结 md"（AI 是过程），
而 JD 职责里还有"**将大模型、AI Agent、RAG 等能力集成到应用中**"（AI 是功能）。

**决策**：两个都做，但产品内 AI 只做一个场景并做深。

- 只做「**AI 转码参数顾问**」一个场景。撒胡椒面同时做 AI 字幕、AI 画质增强，
  三天内每个都做不透，而且都不可验证 —— 正好踩中"不要做的东西自己都用不明白"这条。
- 开发过程记录走 SESSION_LOG，重点写 AI 出错和我如何修正。

**为什么选"参数顾问"这个场景**：它是这个产品里**唯一真正需要语义理解**的环节。
缩放、码率这些参数普通用户根本看不懂，但他们知道自己要"发朋友圈"还是"存档"。
把自然语言翻译成参数，是 LLM 在该场景下不可替代的价值，不是硬凑的 AI 噱头。

## 3. LLM 输出必须结构化，且不给命令执行权

**决策**：模型只输出 JSON（`response_format: json_object`），且**只能从枚举里选值**，
命令字符串由程序拼装，模型碰不到。

**三条防线**：
1. **枚举约束**：`scale` 只允许 `原画|1080p|720p|480p`，`codec` 只允许本机实测可用的编码器
2. **schema 校验**：`plan_schema.py` 逐字段校验，越界一律 clamp 并记录 warning 在界面标黄
3. **能力注入**：提示词里写明本机真实可用的编码器，模型不会推荐一台跑不动的硬件编码器

**为什么不直接让模型输出命令行**：一句精心构造的输入就能让它拼出任意 ffmpeg 参数
（比如写到任意路径）。结构化 + 枚举 + 程序拼装，是把这个风险从根上切掉。

## 4. 无 Key 时降级为"完整的本地规则引擎"，而不是禁用功能

**决策**：无 API Key 时走 `local_rules.py`，**同一套 schema、同一个界面**，
界面明确标注"本地规则"而不是静默降级。

**理由**：审核人第一次打开时大概率没有配 Key。如果那一刻 AI 功能是残的，
那么"集成了大模型"这件事在他眼里就等于不存在。
本地规则引擎覆盖朋友圈 / 短视频 / 邮件 / 会议录屏 / 存档 / 移动端六个场景，
每个都给出理由——有无 Key 都是完整可用的产品，只是"大脑"不同。

## 5. 编码器探测只做两级，坚决不探测"能探但用不了"的

**决策**：只探测 `h264_nvenc` → `libx264`，不做 QSV / AMF。

**理由**（这条是踩坑后改的，详见 SESSION_LOG 第 2 条）：
- AMF 在无 AMD 显卡的机器上会"探测通过但输出无效"，是假阳性
- QSV 在笔记本双显卡上失败率极高
- **`params.py` 只实现了这两种编码器的参数分支**

探测能力必须和实现能力对齐。能探测但不会用，就是在制造误导。

## 6. 范围取舍与熔断记录

**实际可用时间 18 小时**（收到题目时已是第二天下午），初始估算是 35 小时。

## 7. 其它小决策

| 决策 | 理由 |
|---|---|
| LLM 客户端用标准库 `urllib`，不用 httpx/requests | 少一个依赖就少一个"审核人机器上缺包"的可能，打包也小 |
| 转码用 `QProcess` 而不是 `QThread + subprocess` | QProcess 天生异步、走事件循环，不需要自己管线程生命周期，进度信号直接回 UI 线程 |
| 探测/抽帧用 `QThreadPool` | 这些是同步子进程，必须离开 UI 线程 |
| 取消用写 `q` 而不是 `terminate()` | `terminate()` 留下的是播不出来的截断文件；写 `q` 会让 ffmpeg 正常写 trailer |
| 日志落 `%APPDATA%\VideoBox\logs` + 菜单入口 | `--noconsole` 打包后异常不弹窗，没有日志等于盲人摸象 |
| 工作线程只产出 `QImage` | `QPixmap` 跨线程使用会直接崩 |
| 打包用 onedir 而不是 onefile | onefile 每次启动都要解压到临时目录，冷启动慢 5-10 秒，体验差 |

## 8. 如果重来一次

- **先跑通打包再看界面**。打包坑（资源路径、Qt 插件）和界面坑是两套独立问题，
  混在一起排查会互相干扰。
- **更早做自动截图**。第 6、7 个 bug（文字裁切、样式丢失）都是**纯视觉问题**，
  单元测试永远发现不了。`scripts/e2e_ui.py` 应该在第一版界面之后就写。
- **探测命令要用真实输出而不是 `-f null`**。硬件编码器在 null muxer 上的行为有坑，
  一开始就用临时文件能少走一轮弯路。
